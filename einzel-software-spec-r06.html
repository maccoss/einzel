Einzel: an open‑source, agent‑native ion‑optics platform

A C# simulation core, a Python extension surface, a scriptable CLI, a WPF shell, and an MCP server. Covering DC and RF ion optics across nine decades of pressure, and designed from the engine outward for an AI agent to build on.

CodenameEinzel (provisional)
CoreC# / .NET 10
ExtensionsPython
Primary surfaceCLI, in a project folder
FiguresSVG, PDF, VTU

Rev 0.6 adds the artifacts that leave the platform, and drawing that boundary turned out to be as much about restraint as capability. Vector figures and animations are real gaps in the incumbent and worth building. A general-purpose 3D field visualizer is not, because a free one already exists and is better than anything this project would plausibly write. §17 says both things explicitly, so the second can be argued with rather than discovered three years in.

1. Thesis and scope §1

The two differences, and why they are one

Open source and free. No licence, no seat count, no barrier to a student or a collaborator running the same model.

Agent-native. Designed so an agent can author models, run studies, interpret results, and write new capability into the platform, in a loop that closes in seconds.

These reinforce each other. An agent working against a closed binary infers behaviour from documentation and guesses the rest. An agent working against Einzel can read the implementation. Open source is not only a licensing position here; it is a capability of the agent interface.

The corresponding danger

Agent-friendliness makes wrong answers cheaper to produce. An agent generating fifty plausible funnel transmission numbers in an afternoon, three of them computed outside the validity of the model used, is worse than SIMION — because SIMION is slow enough that a human looks at each one, and because someone will believe the fifty. If agents are the headline feature then guardrails (§4) are the headline safety requirement, specified as hard engine behaviour rather than advice.

What this is not

  • Not an accelerator lattice code.
  • Not a gas dynamics solver. Einzel consumes pressure and neutral-velocity fields; it does not compute them.
  • Not a collision cross-section predictor.
  • Not instrument control software, and not a data pipeline.
  • Not a general-purpose visualization application. New in rev 0.6 and argued in §17: fields and trajectories export to VTU, and ParaView does the rest.

The examples corpus is a feature

SIMION has decades of forum posts, example files, and published geometries in the training data of every model an agent might run on. Einzel has none of that. The counter is to be self-describing at runtime and to ship a corpus an agent can pull into context.

EX-1 Ship at least thirty validated reference models spanning every device class, each with a prose description, expected results, and assertion tolerances. EX-2 The corpus runs in CI; a failing example blocks release. EX-3 Examples are enumerable and fetchable from both surfaces.

3. The project as the unit of work §3

A project is a directory. Everything defining a modelling effort is files under one root, and every operation is a command run against that root. This is what enables the agent loop: read files, edit files, run commands, read output. No protocol, no session.

Three format properties, justified without reference to version control

  • PRJ-1 Models, studies, extensions, render specs, and results are text.
  • PRJ-2 Large artifacts are referenced by content hash, never embedded.
  • PRJ-3 A run manifest fully determines its run. Model hash, seeds, engine version, transport mode, solver settings, extension identities. Results are therefore regenerable rather than precious.

Version control is optional and first-class

PRJ-4 A plain folder is the default and fully supported. Every feature, guardrail, and agent workflow works in a directory with no repository. Requiring one would reinstate exactly the barrier §1 exists to remove.

PRJ-5 Version control, where wanted, is scaffolded. einzel init --vcs git writes an ignore file excluding .einzel/, an AGENTS.md, and a starter layout.

PRJ-6 Nothing depends on a hosting provider.

Agent instructions in the project

An agent needs two distinct things: how to use Einzel (platform knowledge, reachable from the user's project since they installed rather than cloned) and how to work on this instrument (local conventions, targets, what has been tried).

AGD-1 einzel init writes an AGENTS.md containing both layers, the first generated and clearly delimited.

Generate, never hand-write, the platform layer

Instructions shipped with v1.2 that describe v1.0 behaviour are worse than none, because an agent trusts them and cannot detect the drift. einzel agents-md emits guidance matched to the installed version and stamps it; einzel doctor reports when a project's stamp is behind.

PRJ-7 A project may declare assertions — expected resolving power, transmission floors, envelope constraints — runnable as einzel test. An agent that edits a model gets immediate pass or fail with a specific figure of merit and a specific delta.

4. Guardrails §4

RequirementStatement
GRD-1No bare numbersEvery quantitative result carries value, units, uncertainty or confidence interval, the ensemble size or convergence measure behind it, and any active warnings. The API offers no way to obtain the value alone.
GRD-2Warnings propagateValidity warnings travel with the result through every layer — engine, command layer, CLI output, MCP response, exported file, rendered figure and video.
GRD-3Warnings above threshold are not suppressibleValidity violations cannot be silenced by any caller, including in batch mode.
GRD-4Validity is checked, not assumedRegime applicability, mesh convergence, ensemble convergence, adiabaticity, and the §10 linearization residual are computed and reported.
GRD-5Preview results are labelled and cannot be promotedTagged permanently; cannot be quoted, exported, fed to an optimizer, or rendered without visible distinction (§17).
GRD-6Extension results are attributedCarries the extension identity and version; cannot present itself as first-party.
GRD-7Results are immutable and traceableEvery result references a manifest. Every rendered artifact references a result.
GRD-8Spending is deliberateAny operation exceeding a configurable cost threshold requires a prior estimate.
GRD-9Human work is never silently lostWhere an agent and a human share a live model, mutations are attributed in a shared linear journal.
GRD-10Drift is detectable, in both directionsA stored result can be checked against both the current model and the currently installed engine.
GRD-11Known-defective versions taint their outputA result produced by a version below the published floor (§18) carries a non-suppressible defect warning. The run is never blocked.
GRD-12A rendering never looks more precise than its dataDecimation tolerance, time compression, and preview status are recorded in every rendered artifact (§17).
GRD-10 covers engine drift, and depends on manifests rather than on version control

The manifest records the model hash and the engine version, and the check compares both against what is present. This works in a plain folder, on a network share, anywhere. Model drift is the failure an agent produces most often; engine drift is the one an update produces, silently, across an entire project at once.

Why GRD-1 is stated so absolutely

An agent handed R = 19,800 reports 19,800. An agent handed that value with n = 1000, an interval of ±400, and a warning that pseudopotential validity was exceeded over part of the path can reason about whether to trust it. The absolutism matters because a convenience accessor returning the scalar will be added by someone eventually, and then used everywhere.

5. Extension surface §5

Agents must extend the platform, not only drive it. An extension path requiring C#, a compile, and a restart is not usable in a loop. The language is Python.

Why Python, and what it costs

The alternative considered was an embedded Lua interpreter, which has exactly one real advantage: a pure-managed interpreter is sandboxable almost for free. Against it, both differentiators point at Python — agents write it far more fluently, scientists already know it, and the numerical ecosystem is there. So Python, with the sandbox paid for architecturally, because embedded CPython cannot be sandboxed in-process.

  • EXT-1 An extension declares type, schemas, trust level, resource needs, and a compatible engine version range. The runtime is an implementation detail of the manifest.
  • EXT-2 In-process (CSnakes) for first-party and explicitly trusted extensions. Lowest latency, no isolation.
  • EXT-3 Sandboxed subprocess for anything agent-authored or third-party, and the default. Job objects and a restricted token on Windows, namespaces and seccomp on Linux. No network.
  • EXT-4 Never invoked per integration step. One call per run.
  • EXT-5 Large arrays cross by shared memory with an Arrow or raw-buffer layout, never by JSON.
  • EXT-6 A vendored interpreter ships with the application.
  • EXT-7 Outputs are attributed per GRD-6 and validated against the declared output schema.
  • EXT-8 Before an update is applied, the updater reports which installed extensions fall outside the new engine's compatible range.
The cleanest extension of all

For model authoring specifically, the best extension is not an extension. A Python script in extensions/ that emits a model document has zero coupling to the engine, needs no sandbox because it never runs inside the platform, and is trivially testable.

7. Regimes and transport modes §7

In a funnel at 1 to 10 mbar the collision frequency vastly exceeds the RF frequency and residence time is of order a millisecond; integrating collision by collision is not merely slow, it is the wrong description. In the flight tube at 4×10−8 mbar the ion may not collide at all in 200 µs and every nanosecond matters.

REG-1 Trajectory integration and statistical diffusion are peer implementations of ITransportMode.

REG-2 The engine computes the governing dimensionless numbers along every path and raises a non-suppressible warning when the selected mode is outside validity.

REG-3 In the overlap band both modes run on the same model and the comparison is a supported operation with its own report.

Accuracy classes

  • Class T, timing. Flight-time accuracy in ppm.
  • Class S, statistical. Transmission, acceptance, efficiency, converged to a stated confidence interval.
  • Class B, boundary. Stability and cutoff boundaries resolved to a stated fraction of the scan variable.

Interpolation dominates

The instinct is a higher-order integrator; usually the wrong lever. A trajectory crossing a gridded potential accumulates error from the interpolant's discontinuous derivatives at every cell boundary, and over 105 crossings that error is systematic rather than random. Trilinear interpolation is not permitted anywhere in a trajectory path; the minimum is tricubic with continuous first derivatives; grid convergence is a first-class test.

Determinism

  • Bit-reproducibility across machines is not a requirement. Golden-file comparisons use documented tolerances with stated reasons.
  • Run-to-run reproducibility on one machine is a requirement, and partly an update-policy question — see §18.
  • Parallel reduction order must not affect results.
  • Flight time accumulates with Neumaier compensation.
  • Rendering is deterministic too. The same result and render spec produce byte-identical vector output, so a figure regenerated for a revision does not produce a spurious diff.

9. Domain model §9

Units

Internally SI, double precision, without exception. At every boundary units are explicit and required. {"energy": 4000} is a validation error. Deliberately more annoying than the alternative, because unit ambiguity is the commonest source of silent wrongness and an agent building from prose is the actor most likely to introduce it.

Geometry, parameterization, symmetry

Geometry is a tree of placed primitives and CSG operations, with STEP import where CAD is the source. Every placement is a parametric expression, never a baked number: named parameters with units and bounds; derived parameters as sandboxed expressions; perturbation channels for rigid transforms and surface deformation; and arrays as a first-class construct.

SYM-1 A geometry subtree may declare cylindrical symmetry, a mirror plane, or discrete periodicity. The solver reduces accordingly and the interpolant reconstructs the full field transparently. A 200-ring funnel driven in two RF phases needs two RF basis fields plus a DC gradient, not 200 basis solutions.

Why the native representation is parametric, not a mesh

It is tempting to adopt an established mesh format as the model representation. Resist it. A mesh is already discretized — nodes and elements — and the parameterization above is exactly what makes §13's tolerance work expressible. Bake a design to a mesh and "move this stripe 50 µm and re-solve" stops being sayable. Gmsh's own answer to this is a separate .geo language, which is evidence that its mesh format was never meant to carry parametric intent. Mesh formats are for interchange (§17), not for the model.

Electrodes, gas, sources, sequences

An electrode is a geometry subtree plus an excitation: fixed DC; DC bound to a parameter; a node on a resistive divider chain; RF with amplitude, frequency, phase; an arbitrary waveform; or floating.

GAS-1 A gas region carries species, temperature, a pressure field, a bulk velocity field, and a collision model. The velocity field is easy to omit and hard to notice missing: at funnel pressures the neutral jet off the inlet capillary drags ions and frequently dominates the axial DC gradient.

An instrument is a timed state machine: ordered phases with durations, excitation overrides, transport mode, and transition conditions. SEQ-1 A phase boundary may change transport mode; the conversion is explicit, reported, and named as a source of uncertainty.

10. Field subsystem §10

Phase 1 is a finite-difference multigrid solver on a regular Cartesian or axisymmetric grid with nested local refinement. Straightforward to implement correctly in C#, clean to parallelize and GPU-offload, naturally accommodating of SYM-1, and semantically close enough to SIMION that SIMION becomes a direct cross-validation target. A boundary element solver is the expected later addition — and the point at which unstructured mesh interchange (§17) starts to matter.

Basis superposition, and where it stops

Solve once per electrode at unit potential with others grounded; any voltage set is a weighted sum. Essential, because it turns voltage optimization from a solve-per-iteration problem into arithmetic. It breaks the moment geometry changes, and a tolerance Monte Carlo over 103 perturbed geometries would need 103 full solve campaigns — roughly three weeks of compute for one study.

FLD-1 For each perturbation channel p, cache ∂Φ/∂p by finite difference over a full re-solve. FLD-2 Every sweep runs a stratified validation subset; if the maximum residual exceeds ACC-1 the result is marked invalid, not annotated. FLD-3 Field caches are keyed by content hash over geometry, mesh, symmetry declaration, boundary conditions, and the solver-behaviour version — the last term is not optional, since after an engine update a cache computed by the previous solver is silently wrong and nothing else would catch it.

RF fields

Two paths with the choice explicit: pseudopotential for survey work and guide drift regions, full time-domain integration for mass filters, traps, injectors. RF-1 Time-domain RF requires a minimum sampling of the RF period, enforced rather than advised.

11. Transport engine §11

Trajectory integration

  • Default: adaptive-step Runge–Kutta with per-step error control against the run's accuracy class.
  • Available: symplectic Verlet for long static-field flights, high-order Gauss–Legendre for validation runs.
  • Field-free drift is advanced analytically.
  • Turning points get forced step refinement. The velocity minimum inside a mirror is where relative timing error is largest and where position-error controllers under-refine.

TRJ-1 Trajectory output for rendering is a separately sampled stream with its own cadence, independent of integration steps. Integration steps cluster where the physics is hard, which is not where a picture needs points; and a full step record for 104 ions is unrenderable regardless.

Statistical diffusion

Motion advances as drift under the local effective field plus mobility-driven diffusion, with the neutral velocity field added to the drift term. Step size is set by diffusion length rather than RF period. TRN-1 Mobility is an explicit input with stated field dependence.

TRN-2 Diffusive transport emits a time-resolved density field rather than trajectories, because that is what it computes. This is what §17 renders for a funnel.

Memory and execution

Particles are held structure-of-arrays in pooled double[] buffers. The inner loop allocates nothing, so garbage collection cannot interrupt a run. CMP-1 The scalar reference implementation is never deleted or allowed to rot.

12. Analysis §12

Figures of merit are computed by the engine, since they are what the optimizer, sweep driver, and project tests consume. All are returned per GRD-1.

Class T

  • Resolving power, reported both FWHM-based and fitted, with the peak model named.
  • Peak shape: FWHM, 10 and 1 percent widths, asymmetry, integrated pedestal fraction.
  • Time-of-flight focusing order: coefficients reported so the binding aberration order is visible.
  • Turn-around time and packet emittance for extraction traps and orthogonal accelerators.
  • Synthetic spectra with detector response and digitizer sampling, and wraparound detection.

Class S

  • Transmission itemized by loss surface and mechanism, with intervals. Never "92 percent".
  • Radial compression and exit emittance for funnels and guides.
  • Transit-time distribution, which sets a pipeline's minimum stage time.
  • Thermalization: energy distribution against residence time.

Class B

  • Stability diagram reconstruction in a–q space.
  • Mass filter peak shape and resolution against scan line.
  • Low-mass cutoff for funnels and RF guides.
  • Secular frequency spectrum and isolation efficiency against notch width.

13. Sweeps and optimization §13

A study is a file in studies/ declaring perturbation channels with distributions, a draw count, a seed, an ensemble specification, and figures of merit to record. Output is one row per draw plus a sensitivity ranking — the actual deliverable, since what is wanted is not only whether 100 to 300 µm suffices but which parameter binds first.

Both modes required: stochastic, for the distribution of achieved performance, and one-at-a-time, to attribute variance. Optimization composes objectives from §12, which may be Python extensions. Nelder–Mead for small problems, CMA-ES for larger and rougher ones.

Deliberately deferred

An autodiff-based differentiable simulator would allow gradient-based optimization against high-order focusing. Attractive, but a research project, and building it into the foundation would constrain every kernel for a benefit derivative-free methods largely deliver at this problem size.

14. Model format and library §14

  • JSON, schema-versioned, with a published JSON Schema carrying descriptions and units on every field.
  • Migrations are code, not documentation. Every schema bump ships a migration and a test that a corpus of prior-version models still loads.
  • Large binaries referenced by content hash.
  • Run manifests record model hash, seeds, engine version, solver-behaviour version, transport mode, compute path, extension identities and versions, and machine.

LIB-1 Device templates are data in the same schema as any other model, plus a declared parameter surface. If supporting a new device requires a change below Einzel.Library, either it is genuinely novel physics or the abstraction is wrong. Almost always the second.

The MCP server

Its distinct value is shared live state: an agent operating on the model a human has open, with the viewport updating and both parties writing into one attributed journal. 16. Shell §16

WPF on Windows. The 3D viewport uses Helix Toolkit on its DirectX 11 path; plain WPF Media3D cannot render 104 trajectories interactively.

Required views

  • 3D viewport: geometry, electrode potentials by colour, equipotential surfaces or slices, trajectory bundles coloured by energy, m/z, or fate. Density clouds rather than trajectories for diffusive regions (TRN-2).
  • Figure composer: build and preview a render spec — view direction, section plane, what to include, labels, dimensions — and save it to figures/ as text so it can be regenerated, diffed, and re-run by the CLI.
  • Animation timeline: per-phase playback rates (RND-7), scrubbing, and frame export.
  • Model tree with parameter editing, live validation, units on every field, template instantiation.
  • Sequence editor: the state machine as a timeline, with excitations and transport mode per phase.
  • Results by accuracy class, with uncertainty and warnings alongside the value, never behind a disclosure control.
  • Regime inspector: governing dimensionless numbers along a selected path, violations highlighted.
  • Project view: models, studies, results with model-drift and engine-drift state, and version-control state where present.
  • Extension manager: installed extensions, trust level, versions, compatible engine range, last test result.
  • Journal: command history with agent and human attribution.
  • Update notice: non-modal, dismissible, with the deferral options of UPD-3.

UI-1 The shell owns layout, input, the interactive viewport, and the update check. It owns no physics, no validation rules, no file format knowledge, and no render output — the figure composer edits a spec that Einzel.Render executes, so the same spec produces the same figure from the CLI.

17. Rendering, export, and interchange §17

Three jobs are routinely conflated here and should not be: an interactive viewport for tuning, a publication figure, and an animation for a talk. Different pipelines, different fidelity requirements, different failure modes. A fourth question — what Einzel deliberately does not visualize — turns out to matter as much as the other three.

Where rendering lives

RND-1 Rendering is an engine capability, not a shell feature. Einzel.Render sits below the shell; the figure composer and einzel render are peer consumers of it. It must produce a publication figure headlessly, on Linux, in CI, with no display attached.

This follows from two requirements already in force. AGT-2 says nothing exists only in the shell, and AGT-6 makes visual feedback part of the agent contract — an agent that can look at the geometry catches errors that no amount of JSON inspection surfaces. Rendering in the GUI only would break both.

RND-2 A render spec is text, lives in figures/, and is versioned with the model. The figure in a paper is regenerable from the repository rather than being a file someone once exported.

Vector output

This is a real gap in the incumbent. SIMION's output is essentially screenshots, so publication figures get redrawn by hand in an illustration program, and the redrawn figure then drifts from the model it depicts. Closing that loop is worth doing properly.

  • RND-3 2D sections and orthographic projections emit SVG and PDF, through a geometric projection pipeline that produces paths rather than pixels. This is a separate pipeline from the DirectX viewport, not an export from it. Publication figures are overwhelmingly of this kind — the companion memo's own figures are line drawings with dimensioned callouts.
  • RND-4 Shaded 3D perspective is raster. Hidden-surface vector output is a deep rabbit hole with poor payoff. Schematic 3D with hidden-line removal may be added later as vector; it is not first.
  • RND-5 Trajectories are decimated with a stated geometric tolerance (ACC-7), because 104 polylines of 105 points each is an unopenable file. The tolerance is recorded in the output per GRD-12.
  • RND-6 Text stays text. Labels, dimensions, and axis annotations are selectable and editable in the output, so a figure can be relabelled for a different venue without regenerating it.
  • Formats are SVG and PDF. EPS is not supported.

Animation

Linear time makes an instrument animation useless

The timescales in a single instrument span six orders of magnitude: an RF period near 1 µs, a mirror turning point in nanoseconds, a flight of 200 µs, a funnel transit of about a millisecond. Played at any single rate, an animation is one blur and a great deal of nothing. Worse, a viewer cannot tell which they are looking at, so a video that compresses time silently misrepresents the physics to exactly the audience least able to check it.

  • RND-7 An animation declares an explicit non-linear time mapping — playback rate per sequence phase — and the current rate is displayed on screen throughout playback. Neither part is optional. This is the animation equivalent of GRD-1: the artifact may compress, but it may not hide that it compressed.
  • RND-8 Diffusive regions animate as evolving density fields, never as particles (TRN-2, and the render row of Fig. 4). Drawing lines through a funnel depicts something the model never computed.
  • RND-9 Native output is an image sequence. Encoding to a video container is an optional out-of-process step using a tool the user supplies. This is a licensing decision as much as an architectural one — see below.
  • RND-10 Videos carry provenance visibly, as a corner stamp with engine version and model hash, in addition to container metadata. A video is the artifact most likely to be shown to an audience with none of the uncertainty apparatus attached, and metadata nobody opens is not provenance.
  • RND-11 Preview-tier results are visually distinguishable in any rendered output (GRD-5). A preview-quality animation shown at a conference is precisely the promotion GRD-5 exists to forbid.

Interchange, and the boundary

RND-12 Fields, trajectories, and density clouds export to VTK/VTU.

The consequence is deliberate and worth stating as a scope decision rather than leaving implicit: the built-in viewport never has to become ParaView. ParaView is better at 3D field and trajectory exploration than anything this project would plausibly build, it is free, and it is already familiar in adjacent instrument communities. One writer buys an entire visualization application. What remains for the viewport is interactive tuning, agent-inspectable renders, and publication vector figures — three jobs it can do well. Anything beyond them is an export, and that boundary should be defended.

Mesh formats: the format and the library are separable

RND-13 Gmsh MSH is supported for import and interchange, through an Einzel-authored reader and writer. GPL attaches to Gmsh's implementation, not to the format; parsing .msh carries no licensing obligation, as several permissively licensed tools demonstrate. The obligation would come from linking the library, which this does not do.

RND-14 MSH is interchange, never the native representation, for the reason given in §9: a mesh is already discretized and cannot carry the parametric intent that makes tolerance work possible.

RND-15 Where meshing itself is eventually needed — with the boundary element solver, not before — Gmsh is detected, not bundled. Shelling out to a GPL binary the user installed separately is clean; shipping it inside the installer drags its distribution obligations along. Identical pattern to the video encoder, and to any future solver dependency.

18. Distribution and updates §18

The conflict this section exists to resolve

A tool that moves files can update itself silently and lose nothing. Einzel computes numbers. If the engine changes under a study — between the first sweep and the tenth, or between a run and the run it is being compared against — the results are no longer comparable, and nothing about the output looks different. Silent update and reproducibility are in direct tension, and the resolution is to make every version change visible, deliberate, and recorded.

Distribution

  • DST-1 Windows: a per-user installer requiring no administrator rights, so it works on a locked-down instrument PC, published as an asset on the GitHub release.
  • DST-2 Portable zip alongside, for machines where installing is not permitted.
  • DST-3 Linux: a tarball, engine and CLI only. No installer and no silent updater.
  • DST-4 SHA256SUMS.txt published with every release.
  • DST-5 Releases are built by CI on a version tag. Nothing distributed is ever built locally.
  • DST-6 The vendored Python runtime ships in the installer and the tarball.
  • DST-7 Optional external tools are detected, never bundled: the video encoder (RND-9) and, later, Gmsh (RND-15). Their absence degrades a feature; it never blocks the platform.

Builds are unsigned for now. SmartScreen will warn on first run and the documentation will say so plainly. This is a real cost — an adoption tax on exactly the cautious institutional user this project wants, and telling people to click through a security warning is a habit worth not teaching. Accepted deliberately at this stage and revisited if the user base grows beyond the lab and its collaborators.

Update policy

  • UPD-1 The shell is the only component that checks for updates, and only at launch. No periodic timer, no background polling.
  • UPD-2 The CLI never contacts the network. einzel doctor reports from a cache the shell writes; --check performs an explicit live check because the user asked. This is what makes AGT-8 true.
  • UPD-3 Updates are never forced. Install on exit, remind next launch, remind in thirty days, skip this version. No option is nagged, escalated, or removed after repeated deferral.
  • UPD-4 The notice is non-modal.
  • UPD-5 A project may pin an engine version. A pinned project run under a different version reports the mismatch and exits with a distinct code rather than silently proceeding.
  • UPD-6 An update never applies while a run, sweep, or solve is active, and never mid-session. Staged on download, applied on next launch.
  • UPD-7 Applying an update regenerates the platform layer of AGENTS.md in projects opened afterward.
  • UPD-8 Before applying, the updater reports what will change: extensions falling outside the new engine's compatible range, whether field caches will be invalidated by a solver-behaviour version change, and whether any project pins would be violated.
  • UPD-9 Linux and portable installs never self-update. einzel self-update is always explicit.

The version floor, without coercion

A published policy file declares a minimum version and, critically, the reason. The lab tool this pattern comes from refuses to start new work below the floor. Einzel does not.

  • UPD-10 A version below the floor keeps working normally.
  • UPD-11 Every result it produces carries a non-suppressible defect warning naming the defect (GRD-11), propagated to exports, figures, and videos by GRD-2.
  • UPD-12 einzel verify reports which stored results were produced by a version now known defective. This is the recall mechanism, and it works retrospectively on results computed before the defect was discovered — which blocking cannot do at all.
Why taint beats blocking

A block is defeatable: the user pins an old version, declines the update, or runs the portable copy. It also punishes exactly the person who has done nothing wrong, mid-work. A taint does neither. It travels with the artifact, survives being copied into a document or emailed to a collaborator, and is visible to whoever eventually reads the number — which is the person the warning is for. It is the same principle as GRD-1, GRD-5, and GRD-12: the platform never stops you working, it refuses to let a result look cleaner than it is.

19. Validation and test §19

  1. Analytic. Parallel-plate and coaxial fields against closed form; ideal single-stage reflectron focusing; Mathieu stability boundaries recovering the standard a–q diagram, the best single test that the RF path is correct; free-flight timing to machine precision; mobility-limited drift velocity against Nernst–Einstein.
  2. Convergence. Every physics test at two mesh densities and two tolerances, asserting observed convergence order against nominal.
  3. Cross-mode. Trajectory integration against statistical diffusion in the overlap band, agreement within Class S intervals.
  4. Examples corpus. The EX-1 models run in CI with their stated tolerances. A failing example blocks release.
  5. Rendering. New in rev 0.6. Vector output is generated headlessly in CI and compared against golden SVG, which is text and therefore diffable — a rendering regression shows up as a readable diff rather than a pixel comparison. Decimation is separately asserted to stay within ACC-7 by measuring deviation from the undecimated path.
  6. Cross-version. Every release runs the examples corpus against the previous release and reports any figure of merit that moved. An intended change is documented and bumps the solver-behaviour version; an unintended one is a regression. Without this, "should I update?" has no answerable form.
  7. Cross-code. Curated geometries with SIMION results as golden files. Not in CI, since it needs a licence.
  8. Literature regression. Published reflectron, MR-TOF, quadrupole, and funnel geometries reproduced against reported performance. These catch conceptual errors rather than numerical ones.
  9. Agent acceptance. Scripted prose tasks run against an agent given a project directory, the CLI, and nothing else. Success rate tracked as a release metric, with a separate track measuring whether agents act on warnings, by seeding tasks whose obvious approach is regime-invalid and scoring whether the agent notices.

TST-1 Every performance path is tested against the scalar reference. TST-2 Every golden-file tolerance carries a comment explaining its magnitude.

21. Delivery phases §21

Three sequencing principles

Seams first, implementations later. Transport mode, symmetry, accuracy class, the device library, and the extension host are designed and stubbed in Phase 1 with one implementation behind each.

The schema and the CLI are Phase 1 deliverables. An agent can do real work at the end of Phase 1, which de-risks the thesis early.

VTU export lands in Phase 1, before any GUI exists. One writer, cheap, and it gives Phase 1 a complete visualization story through ParaView while the shell is still a year away. This is the clearest dividend of the §17 boundary.

22. Risks §22

  1. Agent-generated confident wrongness. The defining risk of the thesis. Mitigation is the whole of §4, and specifically the warning-response track in §19. Measure this, do not assume it.
  2. A figure or video outlives its model and is believed. New in rev 0.6, and arguably the highest-reach failure in the document: a rendered artifact travels further than any other output, is seen by people who never saw the model, and is the one most likely to be shown to an audience. Mitigation: GRD-12, RND-10, RND-11.
  3. An animation misrepresents the physics through time compression. Six orders of magnitude of timescale cannot be shown honestly at one rate, and a viewer cannot detect the compression. Mitigation: RND-7, with the rate on screen rather than in documentation.
  4. Stale results reported as current. The most likely everyday agent failure. Mitigation: GRD-10, with einzel verify in the generated AGENTS.md workflow.
  5. An update silently changes results mid-study. Mitigation: the whole of §18, plus the cross-version test tier that makes the change visible before anyone accepts it.
  6. Field caches survive an update and are silently wrong. Mitigation: FLD-3 keys on the solver-behaviour version; UPD-8 reports invalidation before applying.
  7. Nobody updates, and defective versions persist. The cost of not forcing updates, accepted deliberately. Mitigation: GRD-11 taint and UPD-12 retrospective reporting.
  8. Scope creep into building a visualization application. The pull is constant and each step is individually reasonable. Mitigation: the §17 boundary, stated explicitly so it can be defended rather than eroded.
  9. Silent regime extrapolation. A funnel modelled by trajectory integration produces a plausible number with no sign it is meaningless. Mitigation: REG-2, non-suppressible.
  10. Interpolation error swamps the timing budget. The likeliest route to wrong numbers in Class T work. Mitigation: ACC-3 as a hard gate, convergence testing in CI from the first commit.
  11. Unsigned builds teach click-through. Accepted for now; the habit is the cost, not the warning.
  12. Generated agent instructions rot. Mitigation: generation derives from the same metadata as the schema and help text; UPD-7 regenerates on update.
  13. Sandbox escape or resource exhaustion from agent-written extensions. Mitigation: subprocess isolation as the default, OS-level enforcement.
  14. Third-party extension repositories as an instruction-injection surface. Mitigation: extension-supplied instructions are surfaced for review, never silently merged.
  15. The linearized-field assumption fails at the tails. Spike this in Phase 1.
  16. Schema churn breaks agent workflows. Mitigation: the Phase 1 stability review, migrations as code, a deprecation policy.
  17. Symmetry reduction is harder than it looks. SYM-1 is load-bearing for funnels.
  18. Validation against SIMION takes far longer than budgeted. Historically the largest overrun in this class of project.
  19. The examples corpus rots. Mitigation: CI enforcement as a release gate.
  20. GC pauses in long runs. Preventable with allocation discipline from the start.

23. Decisions still open §23

  1. Einzel availability on NuGet, GitHub, and as a mark.
  2. Whether Phase 1 spikes the FLD-1 linearity assumption before Phase 2 commits. Recommended: yes, two weeks.
  3. Whether hidden-line 3D vector output is worth building at all, or whether sections plus raster stills cover every figure anyone actually publishes.
  4. Whether the provenance stamp on figures is default-on or opt-in. Default-on is safer and will annoy someone preparing a journal submission; a defensible compromise is default-on with an explicit flag that records its own use in the file metadata.
  5. Whether to write the VTU writer or depend on a permissive VTK-adjacent library. Writing it is probably a week and removes a dependency.
  6. What triggers revisiting code signing. A user count, an external institution adopting it, or a first public release.
  7. What the defect-floor policy file contains beyond a version and a reason: whether a defect is scoped to an accuracy class, a device class, or a specific figure of merit, so the taint can be precise rather than blanket.
  8. What the agent acceptance suite measures and what pass rate gates a release. Needs designing before Phase 1 ends.
  9. Whether the in-process extension runner is worth shipping at all, or whether sandboxed-only is simpler and sufficient.
  10. Whether the funnel benchmark uses a published geometry or one of ours.
  11. Governance if this becomes a collaboration: contribution policy, extension registry, and whether instrument-specific models live in the public repository.
